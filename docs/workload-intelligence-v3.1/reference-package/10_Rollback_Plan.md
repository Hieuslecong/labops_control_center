# Release and rollback plan

No production deployment or restart authorized by this prompt. Prepare instructions for a separate approved rollout. Use existing blue-green deployment tooling (`scripts/deploy-zero-downtime.sh` at baseline; verify current path) and single worker handling without editing Zalo settings. Workload feature defaults off in production; read-only and action flags separate if repository supports. Prefer existing flag convention. Record exact artifact versions and migration heads, restore instructions, responsible operator, approved change window, health checks.

## Staging release sequence
1. G0 record current SHA, working tree, existing deployment version, route/BFF/auth, baseline test and performance, protected path snapshot. Use isolated dev/staging data and fake process backend. Never back up secrets into package.
2. Complete G1–G3 with read-only feature. Validate all snapshot invariants, table/filter/coverage/legacy consumer tests. Capture 4 tabs in light/dark/mobile; verify unavailable historical panels. G4 read-only history capability; any optional V2 additions deferred unless approved. Validate query budget and schema compatibility. No migration if not required.
3. G5 validates identity/authorization/protected process/pidfd/operation idempotency in fake backend. G6 activates new actions only in isolated testing if all prerequisite tests pass. Keep legacy action UI unchanged. G7 full regression, visual and performance comparison; publish `GATE_STATUS.md` and test evidence. If blocked, release candidate not ready; no claim of PASS.
4. Before any later approved production rollout: confirm no overlapping Zalo work, check existing deployment's worker ownership, get backup/restore evidence for DB if additive migration necessary, test old/new combinations and migration order. Prefer deploy compatible backend then read-only UI then action enablement only after separate approval. Verify service health, auth, coverage, last-good behavior and no unexpected changes to process/controller settings. Do not kill any real job to test.

## Rollback triggers
- Any unauthorized read/write, cross-role cache exposure, incorrect target identity, unexpected action execution, false success on partial/unknown result, incorrect missing-to-zero semantics, loss of legacy functionality, regression in Zalo shared consumer, excessive collector load, incompatible agent/schema, failed health check or migration conflict. Stop release immediately; disable new actions first, then read-only feature if necessary. No automatic retry of ambiguous action.

## Recovery steps (only after approval)
- Turn off action capability; route new requests through legacy UI/approved previous artifact. Invalidate new feature query caches on session/flag change. Stop accepting new feature actions; inspect outstanding operation state and reconcile without replaying signal. Preserve audit results.
- Roll back application artifact using existing blue-green rollback procedure, not a git reset of user work. Verify old app compatibility with additive schema and new agent. Leave additive safe schema in place if old app compatible; never auto-drop tables or delete shared telemetry/audit to roll back UI. If migration unsafe, use tested operator-approved restore plan with explicit data-loss analysis and backup, not destructive default.
- Re-run health checks, admin and researcher read paths, existing process protection tests with fakes, Zalo compatibility checks read-only, no message delivery tests on production. Record trigger, timestamps, versions, affected data/actions, outcome and residual risks. Keep logs redacted. Resume development in isolated branch; don't merge or redeploy automatically.

Rollback drill evidence required at G7: feature off/on/off staging screenshots, old/new API compatibility, unchanged protected hashes, migration compatibility if used, health check log, known blockers. No release if mandatory rollback drill cannot be performed.
